## Chapter 2: Service Accounts, Workload Identity Federation, and Impersonation — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Max user-managed keys allowed per service account? | 10 external keys per service account. Exam tip: hitting this limit is itself a signal the workload should migrate to WIF/impersonation instead of key rotation. |
| 2 | Default lifetime of a short-lived token from impersonation (generateAccessToken)? | 1 hour (3600s) by default, extendable up to 12 hours (43200s) via the lifetime parameter. Exam tip: shorter lifetime = smaller blast radius if leaked. |
| 3 | Service account keys vs Workload Identity Federation — which does the exam favor? | WIF. Keys are long-lived, exportable, and never expire automatically. WIF issues short-lived tokens with no key material to steal. Exam tip: any 'external workload needs GCP access' scenario → WIF is the correct answer. |
| 4 | roles/iam.serviceAccountUser vs roles/iam.serviceAccountTokenCreator — what's the difference? | serviceAccountUser = attach/actAs a SA to a resource (e.g., Compute instance, Cloud Function). serviceAccountTokenCreator = impersonate the SA to generate short-lived tokens. Exam tip: impersonation for CLI/API access needs TokenCreator, not just User. |
| 5 | Org policy to block ALL service account key creation across an org? | constraints/iam.disableServiceAccountKeyCreation — set to enforced at the organization node. Exam tip: this is the top answer for 'prevent long-lived key creation everywhere'. |
| 6 | Org policy to block uploading externally-generated public keys to a service account? | constraints/iam.disableServiceAccountKeyUpload. Exam tip: distinct from disableServiceAccountKeyCreation — creation blocks Google-managed key generation, upload blocks bringing your own key. |
| 7 | gcloud command to run a CLI command impersonating a service account? | gcloud <command> --impersonate-service-account=SA_EMAIL. Requires roles/iam.serviceAccountTokenCreator on that SA. Exam tip: no key file needed — credential is short-lived. |
| 8 | Command to create a workload identity pool provider for AWS? | gcloud iam workload-identity-pools providers create-aws --workload-identity-pool=POOL --account-id=AWS_ACCOUNT_ID --provider-id=PROVIDER. Exam tip: for generic OIDC use create-oidc; for SAML use create-saml. |
| 9 | One-service-account-per-workload pattern — why does the exam test this? | Each workload gets its own minimally-scoped SA rather than sharing broad-permission SAs. Limits blast radius if one workload is compromised. Exam tip: 'shared service account across multiple apps' in a scenario is almost always the wrong-answer setup. |
| 10 | Default Compute Engine / App Engine service account risk? | Historically granted roles/editor project-wide by default. Exam tip: remediate via custom SA with least-privilege roles, or use constraints/iam.automaticIamGrantsForDefaultServiceAccounts to stop the auto-grant on new projects. |
| 11 | Domain-wide delegation — what's the specific risk tested? | Lets a service account impersonate ANY user in the Workspace domain (configured in Admin console), bypassing per-user consent and per-resource IAM checks. Exam tip: prefer scoped API access or WIF over domain-wide delegation whenever possible. |
| 12 | Cross-project service account usage — what IAM grant is required? | The principal needs roles/iam.serviceAccountUser (or serviceAccountTokenCreator for impersonation) granted directly ON the service account resource, in the project where the SA lives — a project-level role in the consuming project is not sufficient. |
